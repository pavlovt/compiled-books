# Chapter 14: Server-Side Rendering and Hydration

A Svelte component is compiled twice. For the browser, the compiler emits code that creates DOM nodes and wires signals to them. For the server, it emits code that appends strings to a buffer. Server-side rendering (SSR) runs the second kind of output to produce HTML before any JavaScript reaches the browser; hydration runs the first kind against that existing HTML so that the page becomes interactive without being rebuilt. Done well, SSR gives you fast first paint, crawlable content and a page that works before the bundle arrives. Done carelessly, it gives you hydration mismatches, per-request data leaks and inline scripts blocked by your own Content Security Policy.

This chapter is about the Svelte-level mechanics, independent of any meta-framework: the `render` function from `svelte/server`, what the server build runs and skips, the comment markers that make hydration possible, how mismatches are detected and repaired, async SSR (experimental), `hydratable`, CSP and Trusted Types, error boundaries on the server, stable IDs, the classic pitfalls, and a hand-rolled prerendering script with Vite. Frameworks such as SvelteKit call `render(...)` and `hydrate(...)` for you and add routing, data loading and streaming policies; this chapter explains what is underneath.

Examples were compiled and run against Svelte 5.57.2 (server output through `compile(..., { generate: 'server' })`). Generated markup is illustrative and version-specific: the hydration markers are an internal protocol between the server and client builds of the *same* Svelte version, not a stable format.

## `render` from `svelte/server`

```ts
import { render } from 'svelte/server';

render<Comp>(component: Comp, options?: {
    props?: ComponentProps<Comp>;
    context?: Map<any, any>;
    idPrefix?: string;                                     // must not contain '--'
    csp?: { nonce?: string; hash?: boolean };
    transformError?: (error: unknown) => unknown | Promise<unknown>;
}): RenderOutput;
```

`RenderOutput` is `SyncRenderOutput & PromiseLike<SyncRenderOutput>`, where

```ts
interface SyncRenderOutput {
    head: string;
    /** @deprecated use body */ html: string;
    body: string;
    hashes: { script: Sha256Source[] };   // `sha256-${string}`
}
```

`RenderOutput`, `SyncRenderOutput`, `Csp` and `Sha256Source` have been exported since 5.57. The dual nature of the return value is the key design point. If your component tree has no asynchronous work, you can use the result synchronously and read `.head` and `.body` directly. If it contains `await` expressions (the experimental async feature, Chapter 13), you must `await render(...)`; reading `.body` synchronously then throws the server error `await_invalid`. I confirmed both directions: a synchronous tree returned an object whose `then` was a function (it is thenable either way), and a tree with a top-level `await` threw `await_invalid` on synchronous access but rendered correctly under `await`.

A minimal synchronous render:

```ts
// server.ts
import { render } from 'svelte/server';
import App from './App.svelte';

const { head, body } = render(App, { props: { name: 'world' } });

const html = `<!doctype html>
<html lang="en">
    <head>${head}</head>
    <body><div id="app">${body}</div></body>
</html>`;
```

Two observations from running this. First, `render` is lazy in this version: the component function runs when you first read `head`/`body`/`hashes` or call `then`, so errors thrown during rendering surface at that point, not at the `render(...)` call. Wrap the access in your `try/catch`. Second, `Object.keys(output)` is empty because the properties are accessors; destructure them, do not spread the result.

### Options

- **`props`**: the component’s props, typed from the component. Required when the component has required props.
- **`context`**: a `Map` seeded as the root context. Because `createContext` uses private keys, the practical way to provide typed context is a wrapper component that calls the setters (Chapter 12), which “also works with `hydrate` and `render`”.
- **`idPrefix`** (5.22): a prefix for IDs generated by `$props.id()`. Must not contain `--`; otherwise the server error `invalid_id_prefix` (“The `idPrefix` option cannot include `--`”) is thrown. See the section on IDs.
- **`csp`**: `{ nonce }` or `{ hash: true }`; setting both throws `invalid_csp`. Covered below.
- **`transformError`**: converts an error thrown during rendering into a JSON-serialisable value that a `failed` snippet can display. Covered below.

### Output: `head`, `body`, `hashes`

`head` contains whatever `<svelte:head>` elements produced, plus hydration-related scripts and, when `css: 'injected'` is in effect, the component’s `<style>`. In my run, a component with `<svelte:head><title>Hi {name}</title></svelte:head>` and a scoped `p` style produced a head of the form `<!--n50uah--><!----><title>Hi x</title>`: the leading comment carries a hash for the head block, and the title text interpolates props as you would expect. (The documentation for the compile option says that with `css: 'injected'` the SSR output puts `<style>` into the head; with the bundler-plugin default `css: 'external'`, styles are emitted as CSS files that your HTML template must link.)

`body` is the markup for where you mount the app. `html` is the deprecated predecessor of `body`; the runtime defines an `html_deprecated` server error for it (in my 5.57.2 run, reading `.html` on a plain render did not throw), so migrate any template that still uses `result.html`. `hashes.script` lists `sha256-...` source expressions for inline scripts that Svelte inserted, populated when `csp: { hash: true }` is set.

## What the server build runs, and what it skips

The server compile target (`generate: 'server'`) is a different program. For a component with state, derived values and effects, the server output is conceptually:

```js
export default function App($$renderer, $$props) {
    $$renderer.component(($$renderer) => {
        let { name = 'world' } = $$props;
        let n = 1;                       // $state becomes a plain variable
        const d = () => n * 2;           // $derived becomes a function that is called when read
        // ... $$renderer.push(`<p>${$.escape(name)} ${$.escape(d())}</p>`)
    });
}
```

(Illustrative.) Consequences:

| Feature | On the server |
|------------------------------------|------------------------------------|
| `$state`, `$state.raw` | plain variables; no signals, no tracking |
| `$derived`, `$derived.by` | evaluated when read; computed values are rendered |
| `$effect`, `$effect.pre`, `$effect.root` | **never run** |
| `onMount` | **never runs** |
| `onDestroy` | **runs** (once, when rendering the component completes) |
| `{@attach}` and `use:` actions | not run |
| `bind:this` and DOM-dependent bindings | not applicable; initial values are rendered |
| event handlers | not attached; `onclick` etc. emit nothing |
| transitions, `animate:` | do not run |
| `$props.id()` | works; stable between server and client |
| `getContext`/`setContext`/`createContext` | work |
| `$inspect`, `$effect.tracking()` | no-ops or false |

I confirmed this with a component that logged in `onMount`, in `$effect` and in `onDestroy`: only the `onDestroy` message was printed during `render`. `onDestroy` being the only lifecycle function that runs server-side is a documented fact and a frequent source of bugs: code there that touches `window` crashes SSR, and cleanup code that expects a prior `onMount` may run without setup. Guard or avoid it.

The mental model for correctness: **the server renders the component once, from props and initial state, in a single pass.** State changes caused by anything but the render itself cannot occur, so there is nothing to track and the compiler does not emit tracking code. That is also why you must never put necessary logic in effects: it simply will not exist in the server output. The docs’ guidance, “Never wrap the contents of an effect in `if (browser)` or similar — effects do not run on the server”, follows directly.

### Generated markup

Rendering the sample component produced this body (formatted; `idPrefix: 'p'`):

```html
<!--[--><!--$p-s1--><label for="p-s1">x</label><input id="p-s1"/> <!--[0--><p class="svelte-n50uah">x 2</p><!--]--> <!--[--><i>1</i><i>2</i><!--]--><!--]-->
```

Reading it, from the outside in:

- `<!--[-->` … `<!--]-->` bracket the whole component or block: the start and end markers.
- `{#if}` emits `<!--[0-->` for the first branch that rendered (an `{:else}` emits `<!--[-1-->` in 5.57.2, verified by rendering; `<!--[!-->` is used for a boundary’s pending branch). The number identifies *which* branch was rendered on the server, so hydration can detect a different choice on the client.
- `{#each}` is bracketed by `<!--[-->` and `<!--]-->`.
- `<!--$p-s1-->` is a comment emitted by `$props.id()` (prefixed here with `p`).
- `class="svelte-n50uah"` is the scoped-CSS hash class (Chapter 10).
- A third kind, `<!--[?-->`, marks a `<svelte:boundary>` whose `failed` snippet was rendered.

The documentation states the consequence plainly: “You therefore should not remove comments from your HTML output if you intend to hydrate it”. HTML minifiers with comment stripping enabled, CDNs that rewrite HTML, and email-style sanitisers can all break hydration. Configure them to preserve comments, or exclude the app container.

## Hydration

```ts
import { hydrate } from 'svelte';
import App from './App.svelte';

const app = hydrate(App, {
    target: document.getElementById('app')!,
    props: { name: 'world' }
});
```

`hydrate` has the same signature as `mount`, plus `recover`: `{ target, props?, events?, context?, intro?, recover?, transformError? }`. Like `mount`, it does not run effects synchronously (“As with `mount`, effects will not run during `hydrate` — use `flushSync()` immediately afterwards if you need them to”). Unlike `mount`, it reuses the existing DOM: it starts at the first `<!--[-->` comment inside the target, walks the existing nodes in the same order the server emitted them, adopts them, and attaches event listeners, effects and bindings. Intro transitions default to *off* during hydration (the content is already on screen); pass `intro: true` to force them.

The props passed to `hydrate` must produce the same markup as those passed to `render`. In practice that means serialising the server’s props (or the data they were derived from) into the page, parsing them on the client, and passing them in. A mismatch is not a crash; it is a repair or a rebuild, as follows.

### Mismatch handling

During hydration Svelte “walks the DOM, expecting a certain structure”. What happens when reality differs depends on the kind of difference. I ran five scenarios against a component with an `{#if}`, a text interpolation and an `<img src>`:

| Scenario | Observed outcome |
|------------------------------------|------------------------------------|
| Identical server HTML and client props | adopted as-is |
| Text node differs (`7 0` vs. expected `1 0`) | **repaired**: DOM text was updated to the client value |
| `{#if}` branch differs (`<!--[-1-->` where the client expects branch 0) | **repaired**: the block was re-rendered with the client’s branch |
| `<img src="/9">` where the client computes `/1` | **not repaired**: the server value stayed |
| All comment nodes stripped | structure unrecognisable; Svelte discarded the server DOM and mounted from scratch (new comments appeared) |

The documented behaviour matches. For certain attributes: “Certain attributes like `src` on an `<img>` element will not be repaired during hydration, i.e. the server value will be kept. That’s because updating these attributes can cause the image to be refetched (or in the case of an `<iframe>`, for the frame to be reloaded), even if they resolve to the same resource.” That case emits the dev warning `hydration_attribute_changed`. Likewise for `{@html}`: “If the `{@html ...}` value changes between the server and the client, it will not be repaired during hydration” (`hydration_html_changed`), because change detection of arbitrary HTML is expensive. Both are *silent divergences*: the page keeps the server’s value, the client believes it has another, and subsequent updates are applied against a DOM that does not match the client’s idea of it.

When the structure cannot be walked at all, the runtime throws an internal hydration error, warns with `hydration_mismatch` (“Hydration failed because the initial UI does not match what was rendered on the server”), and — by default — **recovers**: it clears the target’s contents and runs a normal `mount`. The `recover` option controls this. In `hydrate`’s implementation:

```js
if (options.recover === false) {
    e.hydration_failed();            // throws: "Failed to hydrate the application"
}
// otherwise:
clear_text_content(target);
return mount(component, options);
```

Recovery costs you the point of SSR (a visible flash and a full client render) but keeps the app working; `recover: false` is for tests and CI where a mismatch must fail loudly. Svelte errors that are not hydration problems (those with a `https://svelte.dev/e/...` link) are re-thrown rather than swallowed, and other exceptions during hydration are logged with `console.warn('Failed to hydrate: ', error)` before recovery.

The most common causes of genuine mismatches:

1.  **Invalid HTML nesting.** The browser’s parser repairs the markup (`<p><div>`, `<table><tr>` without `<tbody>`, `<a>` inside `<a>`) so the DOM differs from the string. Svelte’s compiler rejects many of these at compile time (and warns with `node_invalid_placement_ssr` in cases it can only detect for SSR) precisely to protect hydration.
2.  **Non-deterministic render output.** `Date.now()`, `Math.random()`, locale-dependent formatting (`toLocaleString()` on a server with another locale or time zone), and `typeof window` branches in the template all produce different text on the client.
3.  **Whitespace and comment manipulation** by build tools or proxies.
4.  **Different props or data** between `render` and `hydrate`.

The dev-time `hydration_mismatch` warning is typically preceded by a `console.error` showing the offending HTML. Fix the root cause; do not rely on recovery.

For deliberate divergences — say a value that should be computed from `localStorage` after load — the idiom is to render the server-compatible value first and update after mount:

```html
<script lang="ts">
    import { onMount } from 'svelte';

    let theme = $state<'light' | 'dark'>('light');   // matches the server render

    onMount(() => {
        theme = (localStorage.getItem('theme') as 'light' | 'dark' | null) ?? 'light';
    });
</script>
```

The same two-step trick is documented for forcing an attribute or `{@html}` update on hydration: stash the real value, set it to `undefined` during initial render, restore it in an `$effect`.

## Async SSR (experimental)

With `compilerOptions.experimental.async` enabled (Chapter 13), components may use `await` in the script, in `$derived` and in markup. On the server this means `render` must become asynchronous: “simply await the return value”.

```ts
const { head, body } = await render(App);
```

Semantics, from the docs and verified:

- **Awaits outside `pending` boundaries resolve before `await render(...)` returns.** The result is fully resolved HTML.
- **A `<svelte:boundary>` with a `pending` snippet renders only that snippet on the server**; its content is skipped (“while the rest of the content is ignored”). In my run, a tree with one such boundary and one plain component rendered `<!--[--><!--[!--><p>loading</p><!--]--> <h1>Ann 2020</h1>...`: the boundary’s slot emitted the pending branch (note the `<!--[!-->` marker), the loader inside the boundary was *never called* on the server, and the loader outside it was. The client fills the boundary after hydration. This makes `pending` snippets a deliberate performance tool as well as a UX one: anything behind one is excluded from server render time.
- Synchronous access on an async tree throws `await_invalid`.
- Async SSR needs `AsyncLocalStorage` from `node:async_hooks` (or the platform’s equivalent) to keep per-render context across `await`s; where unavailable the server error `async_local_storage_unavailable` is thrown. Node, Deno and Bun provide it; some edge runtimes need a compatibility flag.
- **Out-of-order rendering** (5.43): independent async regions can complete in any order without the output being delayed behind the slowest sibling’s position in the tree. The docs add, “In the future, we plan to add a streaming implementation that renders the content in the background”, so as of 5.57 `await render(...)` returns only when everything outside `pending` boundaries is done; it is not a streaming API.

Everything about this feature is covered by the same caveat as the client side: details can change outside a major release.

### `hydratable`

The problem: a component that `await`s data renders on the server with the data, but on the client the same `await` runs *again* during hydration, which “blocks hydration for however long it takes”. `hydratable(key, fn)` (5.44) solves it:

```html
<script lang="ts">
    import { hydratable } from 'svelte';
    import { getUser } from '$lib/db';

    // server: runs getUser, serialises the result into the head under 'user'
    // hydration: finds 'user', returns it, does NOT call getUser
    // afterwards: just calls getUser
    const user = await hydratable('user', () => getUser());
</script>

<h1>{user.name}</h1>
```

Behaviour I observed with a Date-valued payload and a nonce:

```html
<script nonce="abc">
    {
        const r = (v) => Promise.resolve(v);
        const h = (window.__svelte ??= {}).h ??= new Map();

        for (const [k, v] of [
            ["user",r({name:"Ann",when:new Date(1588636800000)})]
        ]) {
            h.set(k, v);
        }
    }
</script>
```

The data is embedded as a script in `head`, keyed in a map on `window.__svelte.h`. Notice that the value is a `Date` rebuilt by the script, not an ISO string: serialisation uses `devalue` (`uneval`), which handles `Map`, `Set`, `URL`, `BigInt`, `Date`, `RegExp`, cyclic structures, and, “thanks to some Svelte magic”, **Promises**. A function, class instance or DOM node fails with `hydratable_serialization_failed`, whose message includes the cause.

Rules and failure modes:

- **Requires the async flag at runtime** (`experimental_async_required` otherwise) and, on the server, must run inside a `render(...)` call (`server_context_required`: “Could not resolve `render` context”, for example at module top level).
- **Keys are global to the render.** Calling it twice with the same key and *different* values throws `hydratable_clobbering` (“Attempted to set `hydratable` with key `%key%` twice with different values”), with a stack. Make keys unique, or make identical keys produce identical values. Library authors: prefix keys with the library name.
- **Missing key on the client.** If hydration expects a key that the server did not emit (a component rendered only on the client, or one the server skipped inside a `pending` boundary), the client falls back to running `fn` and warns `hydratable_missing_but_expected`; the corresponding hard error `hydratable_missing_but_required` exists for the stricter case. Both warn that this “forces it to fall back to running its function blockingly during hydration”.
- **It is also a stability tool.** `hydratable('random', () => Math.random())` yields the same value on server and client, which removes a whole class of mismatch from non-deterministic values.
- **Promises** inside the payload let you stream data into the page: the server can resolve them later, and the client sees promises it can `await`.

Frameworks use this behind the scenes (for example SvelteKit’s remote functions); application code rarely calls it directly.

## Content Security Policy

`hydratable` adds an inline `<script>` to the `head`. A strict CSP (`script-src` without `'unsafe-inline'`) will block it, and with it hydration data. Two mechanisms:

**Nonces** for dynamically rendered responses:

```ts
const nonce = crypto.randomUUID();
const { head, body } = await render(App, { csp: { nonce } });

response.headers.set('Content-Security-Policy', `script-src 'nonce-${nonce}'`);
```

The `nonce` attribute is added to the inline script (visible in the output above), on the assumption that you send the same nonce in the header. As the docs put it, a nonce is only valid if used “only when dynamically server rendering an individual response” — generate a new one per response; never cache HTML containing a nonce.

**Hashes** for statically generated HTML (prerendering, CDN-cached pages), where per-request nonces are impossible:

```ts
const { head, body, hashes } = await render(App, { csp: { hash: true } });

response.headers.set(
    'Content-Security-Policy',
    `script-src ${hashes.script.map((h) => `'${h}'`).join(' ')}`
);
```

`hashes.script` is an array of `sha256-...` strings. The docs recommend nonces where possible because “`hash` will interfere with streaming SSR in the future”. Setting both options throws `invalid_csp`. Remember that `hashes` is only populated once the render has produced the scripts, so read it after `await`ing (or after reading `body`).

### Trusted Types and the `fragments` option

Client builds create DOM from `<template>` strings by default. For CSP that includes `require-trusted-types-for 'script'`, that is a problem: assigning HTML strings to `innerHTML` violates the policy. The compile option `fragments: 'tree'` (5.33) makes the compiler emit code that builds nodes one by one instead; `fragments: 'html'` (the default) clones from `<template>.innerHTML`, which is faster. Svelte also uses Trusted Types APIs for HTML handling where the browser supports them (5.51), and `{@html}` accepts `TrustedHTML` values (5.52). If you run with Trusted Types enforcement, set `fragments: 'tree'` in `compilerOptions` and benchmark: you trade some startup speed for compliance.

## Error boundaries on the server

By default, a `<svelte:boundary>` has no effect during SSR: “if an error occurs during rendering, the render as a whole will fail”. `render` rejects (or throws on access), and the request becomes an error response in your server. If a boundary with a `failed` snippet exists, you can opt in to rendering the snippet on the server by passing `transformError`:

```ts
const { head, body } = await render(App, {
    transformError: (error) => {
        console.error(error);            // keep the original with its stack, server-side
        return { message: 'An error occurred!' };   // sanitised, JSON-serialisable
    }
});
```

Rules, from the docs:

- The return value “must return a JSON-stringifiable object which will be used to render the `failed` snippet”. It is serialised into the page and **used to hydrate the snippet** in the browser, so the client renders the same failure UI. In the `failed(error, reset)` snippet, `error` is this transformed value, not the original `Error`.
- If `transformError` itself throws (or rethrows), the whole `render` fails with that error.
- Errors can include sensitive data in `message` and `stack`. Redact; never ship raw errors to the browser.
- If the boundary has an `onerror` handler, it is called upon **hydration** with the deserialised error object, which is how you report the failure from the client too.
- `mount` and `hydrate` accept the same option, defaulting to the identity function, to transform render-time errors before they reach a `failed` snippet or `onerror`.
- Version note: the docs say “Since 5.51”, while the changelog’s “allow error boundaries to work on the server” entry is 5.53.0. Require 5.53 or later.

A boundary that handled a server error is marked in the HTML with `<!--[?-->`, which tells the client to hydrate the `failed` branch rather than the contents.

Since the error object is replaced by a plain value, design `failed` snippets to render from a known shape:

```html
<svelte:boundary>
    <Dashboard />
    {#snippet failed(error)}
        <p role="alert">{(error as { message: string }).message}</p>
    {/snippet}
</svelte:boundary>
```

## IDs: `$props.id()` and `idPrefix`

Form controls, ARIA relationships and SVG `<defs>` all need unique IDs, and the IDs must be identical on the server and the client. `$props.id()` (5.20) returns one per component instance:

```html
<script lang="ts">
    const uid = $props.id();
</script>

<label for="{uid}-email">Email</label>
<input id="{uid}-email" type="email" />
```

It is only valid as the initializer of a top-level variable declaration (`props_id_invalid_placement` otherwise). The server generates it from a per-render counter and writes it into a comment next to the component’s markup; during hydration the client reads the ID back from that comment instead of generating its own, so the two always agree. In my run it appeared as `p-s1` with `idPrefix: 'p'`, and the body carried the matching `<!--$p-s1-->` comment.

The `idPrefix` option (5.22, server `render`) namespaces those IDs. Use it when multiple Svelte apps are rendered into the same document (micro-frontends, islands, widgets), so two independently rendered roots cannot collide. The prefix must not contain `--` (`invalid_id_prefix`). For `mount`/`hydrate` roots there is no prefix option; hydrated IDs must match the server’s, so use the same logic for the server and client entry (the prefix is part of the server output that the client adopts).

Avoid hand-rolled counters (`let id = 0; export const next = () => ++id`) in modules: they are process-wide on the server and diverge from the client’s counter after the first request.

## SSR pitfalls

### Module-level state leaks between requests

The server process handles many requests with the same module instances. Anything stored at module level is shared:

```ts
// state.svelte.ts: DANGEROUS in SSR
export const session = $state({ user: null as null | { id: string } });
```

If any request assigns `session.user` during rendering, the next request may render with another user’s data. The documentation is blunt: “…then the data may be accessible by the *next* user. Context solves this problem because it is not shared between requests.” This includes `writable` stores, caches, singletons and plain `let` variables. Rule of thumb: on the server, mutable module state is guilty until proven client-only. Create per-request instances, provide them with context (via a wrapper component or from the root component), and pass `props`.

A related trap is `Math.random()`/`Date.now()` at module scope: evaluated once per process on the server and once per page load on the client, so they never agree.

### Browser-only APIs

Code that runs during component initialisation runs on the server. `window`, `document`, `localStorage`, `matchMedia` and `navigator.geolocation` are undefined there. Put such code in `onMount`, `$effect` or `{@attach}` (none runs on the server), or in event handlers. Do not “fix” with `typeof window !== 'undefined'` branches in markup-affecting code: that guarantees a mismatch. Libraries that touch the DOM at import time must be loaded dynamically in `onMount`.

Reactive wrappers that read browser state have server fallbacks. `MediaQuery` from `svelte/reactivity` accepts a `fallback` for the server (default `false`), and the window readers in `svelte/reactivity/window` (`innerWidth`, `scrollY`, `online`, …) have `.current === undefined` on the server. The documentation for `MediaQuery` warns: “during server-side rendering, there is no way to know what the correct value should be, potentially causing content to change upon hydration. If you can use the media query in CSS to achieve the same effect, do that.” Prefer CSS media queries for layout and reserve JS media queries for behaviour. `prefersReducedMotion` (Chapter 11) is such a case; it is safe because transitions never play on the server.

In the server build of `svelte/reactivity`, `SvelteMap`, `SvelteSet`, `SvelteDate`, `SvelteURL` and `SvelteURLSearchParams` are simply aliases of the platform classes (`export const SvelteMap = globalThis.Map`), and `createSubscriber` returns a no-op function. Methods newly added to the Svelte classes therefore exist on the server only if the runtime has them (for example `SvelteMap#getOrInsert`, which failed on Node 22 in my run, see Chapter 12).

### `<svelte:head>`

`<svelte:head>` content is emitted into `head` in the render output, and your server template must place it in the document’s `<head>`. It may only appear at the top level of a component. Duplicate `<title>` elements from nested components are all emitted; the last one in the DOM wins in the browser, but for deterministic results keep head management in a small number of layout components. With async SSR, head content inside a `pending` boundary is not rendered on the server.

### Custom elements and SSR

Custom elements (`customElement: true`) compile to `HTMLElement` subclasses, which do not exist on the server, and their shadow DOM contents are not part of normal `render` output. Use components as plain Svelte components for SSR and register custom-element builds only in the browser, or accept client-only rendering for them. Styles for custom elements are always `injected` into the shadow root as a JS string.

### Other server-only errors

- `lifecycle_function_unavailable`: calling `mount` (or similar client-only functions) during render.
- `dynamic_element_invalid_tag`: `<svelte:element this="...">` given an invalid tag name at runtime on the server.
- `server_context_required`: `hydratable` outside a `render` call.
- `async_local_storage_unavailable`: async SSR without `AsyncLocalStorage`.

## Prerendering by hand with Vite

A framework like SvelteKit adds routing, data loading and adapters, but the core of “static prerendering” is small. Here is a minimal Node script, using Vite to compile Svelte in SSR mode, that renders an app to an HTML file and a matching client entry that hydrates it.

Project layout:

```text
index.html             # template with placeholders
src/App.svelte
src/entry-client.ts    # hydrate
src/entry-server.ts    # render
prerender.mjs
```

```html
<!-- index.html -->
<!doctype html>
<html lang="en">
    <head><!--app-head--></head>
    <body>
        <div id="app"><!--app-html--></div>
        <script type="module" src="/src/entry-client.ts"></script>
    </body>
</html>
```

```ts
// src/entry-server.ts
import { render } from 'svelte/server';
import App from './App.svelte';

export function renderApp(props: { name: string }) {
    return render(App, { props, csp: { hash: true } });
}
```

```ts
// src/entry-client.ts
import { hydrate } from 'svelte';
import App from './App.svelte';

const props = JSON.parse(document.getElementById('app-props')!.textContent!);

hydrate(App, {
    target: document.getElementById('app')!,
    props
});
```

```js
// prerender.mjs
import { createServer } from 'vite';
import { readFile, writeFile } from 'node:fs/promises';

const vite = await createServer({ server: { middlewareMode: true }, appType: 'custom' });

try {
    const { renderApp } = await vite.ssrLoadModule('/src/entry-server.ts');
    const props = { name: 'world' };
    const { head, body, hashes } = await renderApp(props);   // `await` also works for sync trees

    let html = await readFile('index.html', 'utf-8');
    html = html
        .replace('<!--app-head-->', head)
        .replace(
            '<!--app-html-->',
            body
        )
        .replace('</body>', `<script id="app-props" type="application/json">${JSON.stringify(props).replace(/</g, '\\u003c')}</script></body>`);

    await writeFile('dist-prerender.html', html);
    console.log('CSP script hashes:', hashes.script);
} finally {
    await vite.close();
}
```

Notes on this recipe:

- `await renderApp(...)` works whether or not the tree is async, because `RenderOutput` is `PromiseLike`.
- The props are serialised into an inert `application/json` script (escaping `<` to avoid `</script>` injection) and re-read on the client, so `render` and `hydrate` receive identical props: the precondition for a clean hydration.
- In a production build, compile the server entry with Vite’s SSR build (`vite build --ssr src/entry-server.ts`) and import the built module in the prerender script, rather than using the dev server; the shown form is the simplest correct one.
- Because the output is static HTML, a CSP must use hashes (`csp: { hash: true }`), not a nonce. Merge `hashes.script` with the hash of your own inline scripts when constructing the header or a `<meta http-equiv>` tag.
- Do not strip comments from `index.html` or the result.
- A CDN or minifier that rewrites HTML is the first suspect when hydration “suddenly” fails in production.

What a framework adds on top: routing and per-route data loading, serialisation of load results, streaming and error handling policies (`transformError`), asset preloading, cache headers and adapters for deployment targets. SvelteKit calls `render(...)` and `hydrate(...)` for you; everything in this chapter describes what it does underneath.

## Debugging checklist

1.  Reproduce with `recover: false` in development so a mismatch throws instead of silently rebuilding.
2.  Read the `console.error` that precedes `hydration_mismatch`; it shows the HTML at the failing node.
3.  Diff the server HTML against `document.body.innerHTML` after load. Look for repaired nesting, stripped comments and different text.
4.  Search for `Date`, `Math.random`, `toLocale*`, `typeof window`, `navigator` and `window.matchMedia` reachable during initialisation.
5.  Treat warnings `hydration_attribute_changed` and `hydration_html_changed` as bugs: they mean the server value is winning silently.
6.  Check that props are identical between `render` and `hydrate`.
7.  For async SSR, confirm that `AsyncLocalStorage` is available, that `hydratable` keys are unique, and that awaits you expect on the server are not hidden behind a `pending` boundary.

## Key takeaways

- `render(Component, options)` from `svelte/server` returns `RenderOutput`: a sync object (`head`, `body`, deprecated `html`, `hashes`) that is also `PromiseLike`. Use it synchronously only for trees without `await`; otherwise `await` it (sync access throws `await_invalid`). It is lazy: errors surface when you read the output.
- The server build is a separate compile target: effects, `onMount`, actions and attachments never run; `$derived` is evaluated when read; `onDestroy` and `$props.id()` do run. Nothing necessary may live in an effect.
- Hydration walks the server’s DOM guided by comment markers (`<!--[-->`, `<!--[0-->`/`<!--[-1-->` for `{#if}` branches, `<!--[!-->` for a pending boundary branch, `<!--[?-->` for failed boundaries, `<!--]-->`). Never strip comments.
- Text and block-branch differences are repaired; `<img src>`, `<iframe>` and `{@html}` differences are not (warnings `hydration_attribute_changed`, `hydration_html_changed`). Unrecoverable structure differences warn `hydration_mismatch` and, unless `recover: false` (which throws `hydration_failed`), the app is rebuilt with `mount`. Hydration does not play intros by default.
- Async SSR (experimental): `await render(App)`; boundaries with `pending` render only the snippet on the server and skip their content; `AsyncLocalStorage` is required; streaming is not implemented in 5.57.
- `hydratable(key, fn)` serialises server results with `devalue` (plus Promises) into an inline head script and returns them during hydration; keys must be unique (`hydratable_clobbering`), it needs the async flag and a render context.
- CSP: `csp: { nonce }` per dynamic response, `csp: { hash: true }` with `hashes.script` for static HTML; both together is `invalid_csp`. For Trusted Types enforcement use `fragments: 'tree'`.
- `transformError` on `render`/`mount`/`hydrate` lets server boundaries render `failed` snippets with a sanitised, JSON-serialisable error that is used to hydrate; `onerror` runs during hydration. Without it, a server error fails the whole render.
- `$props.id()` gives SSR-stable IDs; `idPrefix` (no `--`) namespaces IDs across multiple server-rendered roots.
- Module-level mutable state is shared across requests: use context-scoped instances. Browser APIs belong in `onMount`/effects/attachments; `MediaQuery` and window readers have server fallbacks but can cause visible changes on hydration.
- Static prerendering is a short script: load the SSR module with Vite, `render`, inject `head` and `body`, serialise identical props for the client, and use hashes for CSP.
